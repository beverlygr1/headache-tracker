# SPEC: изменение погоды (weather_change) в предсказании приступа

Статус: **v4**. Этапы 1–5 реализованы (см. раздел 10), этап 5 реализован. Изменения v4: после получения кода выяснилось, что предсказание — это `GET /forecast/risk` без тела; разделы 4.2, 6, 8 (предсказание) и 9 переписаны.

Принцип: каждое утверждение либо взято из присланных файлов / документации (помечено источником), либо явно помечено как **решение**, либо вынесено в **открытый вопрос**.

## 1. Цель

1. Эндпоинт предсказания принимает необязательные `latitude` и `longitude`. Если они переданы, внутри предсказания определяется уровень изменения погоды и переводится в признак модели `weather_change`.
2. Данные о погоде сохраняются в `weather_observations`.
3. Каждое предсказание сохраняется в `predictions`: id пользователя, все входные поля и предсказанная вероятность.

**Open-Meteo**, `GET https://api.open-meteo.com/v1/forecast`. Бесплатный тариф подходит: проект некоммерческий (на странице historical API тарифы разделены на Non-Commercial и Commercial). Open-Meteo просит ссылаться на источник данных — указать в README (решение).

- параметры `latitude`, `longitude`, `hourly`, `timezone`, `past_days`;
- почасовые `temperature_2m`, `pressure_msl`;
- `timezone=auto` определяет зону по координатам (страница historical API).

## 4. Контракты

### 4.1 Сервис погоды

Функция `get_weather_change(latitude, longitude) -> WeatherObservation`: запрос к Open-Meteo, расчёт уровня по разделу 5, запись в `weather_observations`, возврат записи.

Решение: предсказание вызывает эту функцию **внутри процесса**, а не HTTP-запрос к собственному эндпоинту (нет сетевого вызова самим к себе, нет проблем с авторизацией между вызовами). Отдельный `GET /weather/change?latitude=..&longitude=..` остаётся тонкой обёрткой над той же функцией (Q6).

Ответ `GET /weather/change`, 200:

```json
{
  "weather_change": 1,
  "label": "moderate",
  "date": "2026-11-09",
  "timezone": "Asia/Tomsk",
  "details": {
    "delta_pressure_hpa": 4.1,
    "delta_temperature_c": 1.8,
    "pressure_level": 1,
    "temperature_level": 0
  },
  "source": "open-meteo",
  "record_id": 123
}
```

`label`: `0 → "minor"`, `1 → "moderate"`, `2 → "significant"` (решение).
Ошибки: 422 — координаты вне диапазона; 502 — Open-Meteo недоступен / ошибка / `null` в нужных часах. При ошибке в БД ничего не пишется.

Таймаут запроса к Open-Meteo — параметр конфига `weather_timeout_seconds`, по умолчанию **5 с**, повторов нет (решение: при сбое погода просто не учитывается, повтор только задержал бы ответ предсказания). Значение 5 с — моё, не из источника (Q8).

### 4.2 Эндпоинт предсказания: изменения

Факт: `GET /forecast/risk` не принимает признаки от клиента. `predict_probability(db, current_user)` собирает их из дневника (через `build_features`). Поэтому требование «клиент не может прислать `weather_change`» выполняется само собой: поля такого нет, запрещать нечего.

Изменение: два необязательных query-параметра:

| Параметр | Тип | Правило |
|---|---|---|
| `latitude` | `float \| None = None` | `[-90, 90]` |
| `longitude` | `float \| None = None` | `[-180, 180]` |

Порядок обработки:
1. `user_id` = `current_user.id` (из токена).
2. Валидация: переданы оба или ни одного, иначе 422.
3. С координатами: внутри `predict_probability` вызывается `get_weather_change(db, lat, lon)`. Успех → в `build_features` передаётся `weather_change_level` (раздел 6). Ошибка `WeatherUnavailableError` → **погода не учитывается**, предупреждение в лог, предсказание продолжается.
4. Если query-параметров нет: берутся `latitude` и `longitude` записи дневника за сегодня (дата записи = сегодня в часовом поясе пользователя), когда оба заполнены. Если записи нет или координаты пустые — погода не запрашивается, `weather_change` не заполняется (модель получает 0). Это решение пользователя (Q9).
5. Предсказание считает `Predictor.predict`.
6. Запись в `predictions`, коммит одной транзакцией вместе со строкой погоды.

Координаты **не входят в вектор признаков**. В ответ `RiskForecastResponse` добавляется необязательное поле `weather` (то же содержимое, что у `GET /weather/change`), `null` если координат не было или погода недоступна. Поле `weather` добавлено в `RiskForecastResponse` (этап 4).

## 5. Правило определения уровня 0/1/2

### 5.1 Что сравниваем

Решение: «изменение в этот день» = разница между **средним за сегодня и средним за вчера** (по локальной дате точки, `timezone=auto`):

- `ΔP = |mean(pressure_msl сегодня) − mean(pressure_msl вчера)|`, гПа;
- `ΔT = |mean(temperature_2m сегодня) − mean(temperature_2m вчера)|`, °C.

Запрос: `hourly=temperature_2m,pressure_msl&past_days=1&forecast_days=1&timezone=auto` — один запрос возвращает и вчерашний, и сегодняшний день (48 часовых значений). Произвольные прошлые даты не поддерживаются: предсказание делается на «сегодня».

Почему так:
- смысл признака в схеме — «в этот день»; сравнение с предыдущим днём ему соответствует;
- среднее считаем сами: дневные средние в найденной схеме API не подтверждены, а почасовые `temperature_2m` и `pressure_msl` подтверждены;
- берём модуль: модель направление не различает, признак бинарный.

Ограничение: среднее за сегодня включает прогнозные часы, которых ещё не было. Принято, чтобы эндпоинт работал в любое время суток.

### 5.2 Пороги

| Уровень | ΔP, гПа | ΔT, °C |
|---|---|---|
| 0 — незначительное | < 3.3 | < 2.5 |
| 1 — среднее | ≥ 3.3 и < 6.7 | ≥ 2.5 и < 5 |
| 2 — значительное | ≥ 6.7 | ≥ 5 |

Итог: `weather_change = max(pressure_level, temperature_level)`.

### 5.3 Обоснование (честно)

**Устоявшихся клинических порогов не найдено.**
- Обзор в *Current Pain and Headache Reports*, 2024 ([Springer](https://link.springer.com/content/pdf/10.1007/s11916-024-01216-8.pdf)): численных порогов нет; результаты противоречивы (Katsuki — связь с низким давлением; Li — связи нет; Prince — у одних триггер низкое давление, у других высокое; Akgün, Tanik, Li — связи с температурой нет).
- Mukamal et al., 2009 ([PubMed](https://pubmed.ncbi.nlm.nih.gov/19273827/)): OR 1.075 на каждые **5 °C** (температура, сильнейший фактор), OR 0.939 на **5 мм рт. ст.** (давление, слабее). Это эффект на непрерывной шкале, а не порог; температура там — средняя за 24 ч до обращения, а не её изменение; эффект давления — за 48–72 ч и только для не-мигренозных головных болей.

Что сделано: шаги 5 °C и 5 мм рт. ст. (= 6.67 гПа; 1 мм рт. ст. = 1.33322 гПа) взяты как **единица масштаба**: уровень 2 — полный шаг, уровень 1 — половина (2.5 °C; 3.33 → округлено до 3.3 гПа).

Это **инженерные значения по умолчанию, а не клинические пороги**. Поэтому:
1. шесть чисел лежат в конфиге (`settings`);
2. в БД сохраняются сырые `delta_*`, чтобы пересчитать уровни без повторных запросов;
3. рекомендуется калибровка на ваших данных.

Существующие вызовы не меняются. `predict_probability` (в `app/services/forecast.py`, файл ещё не получен) передаёт уровень из `get_weather_change`.

## 7. База данных

Две таблицы (SQLAlchemy-модели + миграции Alembic).

### 7.1 `weather_observations`

| Колонка | Тип | Содержимое |
|---|---|---|
| `id` | PK | |
| `latitude`, `longitude` | float | как переданы в запросе |
| `local_date` | date | локальная дата точки |
| `timezone` | str | зона, определённая API |
| `source` | str | `"open-meteo"` |
| `fetched_at` | timestamptz | время запроса |
| `mean_pressure_msl_today`, `mean_pressure_msl_prev` | float | гПа |
| `mean_temperature_today`, `mean_temperature_prev` | float | °C |
| `delta_pressure_hpa`, `delta_temperature_c` | float | |
| `pressure_level`, `temperature_level`, `weather_change_level` | smallint | 0/1/2 |
| `raw_hourly` | JSON | исходные 48 часовых значений |

Решение: **каждый вызов создаёт новую строку**, уникальности нет. Причина: координаты приходят с клиента как произвольные float, поэтому ключ для кэша ненадёжен, а для учебного проекта объём небольшой. Минус: повторные запросы с одной точки дублируют данные.

### 7.2 `predictions` — все прогнозы

| Колонка | Тип | Содержимое |
|---|---|---|
| `id` | PK | |
| `user_id` | `Integer`, FK → `users.id`, `ondelete=CASCADE`, индекс | `current_user.id` |
| `created_at` | timestamptz | время предсказания (решение: нужно для порядка) |
| 24 колонки признаков | smallint | `stress`, `excess_sleep`, … `attacks_last_7_records` — все поля `PredictionInput`, имена как в `FEATURE_COLS`; значения те, что реально поданы в модель (включая `weather_change`, выставленный сервером) |

Правило записи: строка пишется после успешного расчёта; запись погоды и запись прогноза — в одной транзакции. Если предсказание не получилось, строки нет.

## 8. Критерии приёмки

Погода:
1. Валидные координаты → 200 и запись в `weather_observations`; `record_id` совпадает.
2. Три уровня воспроизводятся тестами на границах порогов (2.49/2.5, 4.99/5, 3.3/6.7), итог — максимум по давлению и температуре.
3. Сбой Open-Meteo или `null` в часах → 502 на `GET /weather/change`, новых строк нет.
4. Пороги читаются из конфига.

Предсказание (`GET /forecast/risk`):
5. `user_id` в `predictions` равен `current_user.id`.
6. Без параметров и без координат в сегодняшней записи дневника: ответ и вектор признаков идентичны прежним; в `predictions` строка пишется, `latitude/longitude/weather_observation_id` = NULL, `weather: null`.
6а. Без параметров, но с координатами в сегодняшней записи дневника: используются они, и в `predictions` пишутся эти координаты.
6б. Query-параметры главнее координат дневника.
7. С координатами и успешной погодой: уровень 2 → в модель `weather_change = 1`; уровни 0 и 1 → `0`; в ответе блок `weather`; `weather_observation_id` заполнен.
8. С координатами и недоступной погодой (мок падения/таймаута/`null`): предсказание успешно, `weather_change = 0`, `weather: null`, `weather_observation_id` = NULL, новых строк в `weather_observations` нет.
9. Передан один из `latitude`/`longitude` или значение вне диапазона → 422.
10. Координаты не попадают в вектор признаков; `prediction_schemas.py` не изменён.
11. В `predictions` пишутся `user_id`, все 24 признака (как поданы в модель) и `probability`, равная возвращённой клиенту.
12. Обе миграции применяются и откатываются.
13. Внешний вызов в тестах замокан.

## Приложение A. Признаки модели, не учитываемые в текущем прогнозе

`build_features` вычисляет 6 из 24: `stress`, `lack_of_sleep`, `excess_sleep`, `excessive_caffeine`, `days_since_last_attack`, `attacks_last_7_records`.

Не вычисляются (всегда 0): `exercise_trigger`, `no_exercise_trigger`, `physical_fatigue`, `menstrual_phase`, `ovulation_phase`, `excessive_emotional_change`, `weather_change`, `excessive_sunlight`, `noise`, `poor_lighting`, `specific_smell`, `excessive_alcohol`, `irregular_meals`, `overeating`, `excessive_smoking`, `cheese_chocolate`, `travel`, `other_trigger`.

Причина: `DiaryValues` содержит только `sleep_hours`, `stress_level`, `caffeine_intake`. После реализации этой спеки закрывается только `weather_change`.

Попутно: описания полей схемы говорят «пациент отметил…», а `build_features` строит `stress`, `lack_of_sleep`, `excess_sleep`, `excessive_caffeine` по числовым порогам (стресс ≥ 7, сон < 6 / > 10 ч, кофеин > 400 мг). Обучался ли датасет на тех же определениях, из файлов не видно.
