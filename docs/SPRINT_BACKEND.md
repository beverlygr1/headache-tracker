# Серверные задачи спринта 12–15 октября

Изменения основаны на `dev`. Они добавляют явную отметку наличия боли и данные для графика, сохраняют существующие поля сводки и не меняют интерфейс Flutter или ML-сервис.

## Обновление сервера

Перед запуском нового API примените миграцию:

```bash
cd backend
pip install -r requirements.txt
alembic upgrade head
```

В Docker Compose миграции выполняются при старте backend. Новая миграция `0003_diary_headache` следует за `0002_onboarding`; старые записи получают `headache_present = null`. При откате до `0002_onboarding` удаляется только новая отметка, остальные записи сохраняются. Миграцию из параллельной ветки аптечки нужно согласовать отдельно: эта ветка не объединяет её автоматически.

Все запросы ниже используют префикс `/api/v1` и заголовок `Authorization: Bearer <access_token>`. Пользователь определяется по токену; чужой `user_id` не нужен.

## Для формы приступа

`POST /attacks` требует только `start_time` и `intensity` (1–10). Остальные сведения необязательны:

```json
{
  "start_time": "2026-10-10T18:00:00+07:00",
  "intensity": 6,
  "pain_type": "Пульсирующая",
  "localization": "Виски",
  "symptoms": ["Тошнота"],
  "medications": ["Препарат, указанный пользователем"],
  "relief_factors": ["Отдых"]
}
```

Ответ `201` содержит ID и все сохранённые поля. `GET /attacks/{id}` и список `/attacks` возвращают эти поля. Время хранится и возвращается в UTC; клиент показывает локальное время.

Несмотря на название метода, `PUT /attacks/{id}` обновляет только переданные поля. Дополнение записи и завершение должны использовать тот же ID. Завершение:

```json
{"end_time": "2026-10-10T19:30:00+07:00"}
```

Пропущенные поля сохраняются. `null` очищает необязательный скаляр, `[]` — список. `end_time: null` снова открывает приступ. `intensity: null`, `start_time: null` и завершение раньше начала дают `422`, сохранённая запись не меняется. Чужая запись даёт `404` при чтении, изменении и удалении.

Фронтендеру нужно провести `pain_type`, `medications` и `relief_factors` через `AttackRecord`, репозиторий, форму и подробности: один сервер эти поля в интерфейсе не отобразит. Проверки API покрывают создание, частичное редактирование, завершение и повторный вход без потери полей.

## Для дневника

`PUT /diary/2026-10-10`:

```json
{
  "headache_present": false,
  "sleep_hours": 7.5,
  "sleep_quality": 8,
  "stress_level": 4,
  "caffeine_intake": 120,
  "water_ml": 1800
}
```

- `headache_present: true` — пользователь отметил боль за эту дату.
- `false` — пользователь явно отметил отсутствие боли.
- `null` — не указано; переданный `null` очищает предыдущую отметку.
- Если поле не передано, прежняя отметка сохраняется.

Принимаются только JSON boolean и null; строки и числа дают `422`. Отсутствие записи приступа не считается отсутствием боли. Отметка дневника не вычисляется из приступов и не меняет их автоматически. Для ML это самостоятельный пользовательский ответ, который может потребовать проверки согласованности.

Единицы: сон — часы (0–24), качество сна и стресс — 1–10, кофеин — мг, вода — мл. Все поля необязательны. Изменение воды не стирает качество сна, кофеин, координаты или отметку боли. Одна запись на аккаунт и дату, повторный PUT обновляет её. GET по дате возвращает `404`, если записи нет.

Для новых полей нужно дополнить клиентскую `DailyEntry` и вызов `DiaryApi.upsert`. Старый клиент продолжает работать и не стирает новую отметку, если не отправляет её.

## Для статистики и графика

Сводка:

```text
GET /analytics/summary?period=week&time_zone=Asia/Tomsk
```

Существующие поля `period`, `total_attacks`, `avg_intensity`, `avg_duration_minutes` сохранены. Добавлены `completed_attacks`, `from_date`, `to_date`, `time_zone`.

График:

```text
GET /analytics/intensity?period=week&time_zone=Asia/Tomsk
```

Пример фрагмента ответа:

```json
{
  "period": "week",
  "from_date": "2026-10-05",
  "to_date": "2026-10-11",
  "time_zone": "Asia/Tomsk",
  "points": [
    {
      "date": "2026-10-05",
      "total_attacks": 2,
      "avg_intensity": 6.0,
      "max_intensity": 8,
      "diary_recorded": true,
      "headache_present": true
    },
    {
      "date": "2026-10-06",
      "total_attacks": 0,
      "avg_intensity": null,
      "max_intensity": null,
      "diary_recorded": false,
      "headache_present": null
    }
  ]
}
```

В реальном ответе есть точка на каждый день выбранного периода, по возрастанию даты. Пример выше сокращён до двух точек. Дневная интенсивность — среднее интенсивностей приступов, **начавшихся** в этот день; максимум возвращается отдельно. Сводка считает среднее по всем приступам, а не среднее дневных средних. Один длинный приступ учитывается один раз, по дате начала.

День без приступов имеет `avg_intensity: null` и `max_intensity: null`. Не превращайте их в нули и не соединяйте линию через пропуски. `total_attacks: 0` означает только отсутствие зарегистрированных начал приступов. Чтобы показать явно отмеченный день без боли, используйте `headache_present: false`. `diary_recorded` отличает отсутствие дневника от дневника без ответа о боли.

По умолчанию `time_zone=UTC`; для локальных календарных дней клиент передаёт IANA-пояс, например `Asia/Tomsk`. `week`, `month`, `year` означают 7, 30 и 365 календарных дат **включая сегодня**. Это уточняет прежние скользящие интервалы по часам и даёт одинаковые границы сводке и графику. Дата группировки определяется после перевода времени начала в выбранный пояс, включая переходы летнего времени.

Для собственного периода передайте обе даты вместо вычисления периода:

```text
GET /analytics/intensity?from_date=2026-10-01&to_date=2026-10-10&time_zone=Asia/Tomsk
GET /analytics/summary?from_date=2026-10-01&to_date=2026-10-10&time_zone=Asia/Tomsk
```

Обе даты включены. Параметр `period` при своих датах остаётся в ответе как выбранное значение (по умолчанию `month`), но фактические границы определяются `from_date` и `to_date`. Максимум — 366 дней. Одна дата без другой, обратный диапазон, неподдерживаемый пояс или крайние непредставимые даты дают `422`.

Будущие начала приступов не участвуют в статистике; будущие даты графика остаются пустыми. Средняя длительность считается только по приступам с корректным завершением не позже текущего момента; длительность берётся целиком, даже если конец выходит за выбранный период. Активные приступы входят в количество и интенсивность, но не в среднюю длительность. В пустой сводке средние остаются `0.0` для совместимости: ориентируйтесь на `total_attacks` и `completed_attacks`, чтобы показать «Нет данных».

Список приступов и CSV сохраняют фильтрацию по UTC; дневник использует введённые календарные даты. Обратный диапазон дат теперь даёт `422` и для списка приступов, дневника и CSV. CSV, анализ триггеров, PDF и контракт ML не расширялись этой задачей.

## Проверка и совместная приёмка

```bash
cd backend
pip install -r requirements-dev.txt
pytest -q
```

Для запуска API-тестов на отдельной PostgreSQL-базе можно задать `TEST_DATABASE_URL`; имя базы должно оканчиваться на `_test`. Тесты создают и удаляют её таблицы. Без переменной используется временная SQLite. Миграционные тесты проверяют сохранение истории, nullable-отметки, откат, повторное применение и PostgreSQL SQL; при PostgreSQL-режиме выполняют и живую миграцию с `alembic check`.

Для общей проверки с фронтендерами:

1. Войти, создать приступ с дополнительными полями, дополнить и завершить тот же ID.
2. Перезапустить клиент и войти снова: дополнительные поля и время завершения должны сохраниться.
3. Отметить день без боли, затем изменить только воду: отметка должна остаться.
4. Открыть сводку и график с одинаковыми датами и поясом: число приступов должно совпасть.
5. Проверить пустой день, пустой аккаунт, неверный диапазон и другой аккаунт.
6. Отключить сеть во время сохранения: форма должна сохранить ввод; это проверяет фронтендер на своём экране.

Новые экраны участников ещё не находятся в `dev`, поэтому общую визуальную приёмку нужно провести после их PR. Серверные сценарии покрыты интеграционными тестами.
