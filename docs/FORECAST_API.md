# API экспериментального прогноза

`GET /api/v1/forecast/risk` рассчитывает вероятность **начала приступа на следующий календарный день**. Требуется `Authorization: Bearer <access_token>`. Профиль, дневник и приступы берутся только из аккаунта владельца токена. Endpoint не принимает дату, user_id или признаки из запроса.

## Время и дата

- `calculated_at` — момент расчёта или проверки достаточности данных в ISO 8601 UTC. Он формируется заново при каждом запросе, не является временем обучения модели и не означает, что прогноз сохранён в БД.
- `prediction_date` — завтра относительно локальной даты этого момента в часовом поясе профиля `time_zone`.
- `time_zone` — реально использованный IANA-пояс, например `Asia/Tomsk`. Если настройка отсутствует или неверна, используется `UTC`. Клиент может сохранить пояс через `PUT /api/v1/user/profile`.
- `horizon_days` — `1`: следующий календарный день, а не скользящие 24 часа после запроса.

Все поля доступны и при недостатке данных. Например, `2026-10-20T18:30:00Z` — уже 21 октября в Томске; целевая дата прогноза будет 22 октября.

## Достаточность входных данных

Для текущей локальной даты нужны все три **явно заполненных** поля дневника:

| Поле | Значение | Ограничение |
|---|---|---|
| `sleep_hours` | Продолжительность сна в часах | 0–24 |
| `stress_level` | Уровень стресса | 1–10 |
| `caffeine_intake` | Кофеин в мг | Целое число ≥ 0 |

Ноль — заполненное значение, `null` — пропуск. Отсутствие кофеина нужно записать как `0`. Вода, качество сна или отметка боли сами по себе не заменяют эти три поля. Вчерашняя или завтрашняя запись не заменяет сегодняшнюю. Требования «накопить 7/14 дней» нет: модель допускает отсутствие истории, но это не подтверждает точность при короткой истории.

Это техническое правило для предотвращения расчёта на полностью или частично нулевых подстановках текущих факторов. Оно не является медицинским критерием достаточности и не гарантирует качество модели. Другие признаки существующей модели по-прежнему используют её штатные значения по умолчанию. Алгоритм признаков и обученный артефакт в этом обновлении не меняются.

## Ответ ready

HTTP 200:

```json
{
  "status": "ready",
  "calculated_at": "2026-10-20T12:00:00Z",
  "prediction_date": "2026-10-21",
  "time_zone": "UTC",
  "horizon_days": 1,
  "risk_level": "42",
  "probability": 0.42,
  "factors": [],
  "recommendations": [],
  "missing_fields": [],
  "message": null
}
```

Вероятность округляется моделью до двух знаков и лежит в диапазоне 0–1. `risk_level` сохранён для совместимости: это строка округлённого процента, а не категория риска. Факторы и рекомендации пока не вычисляются. Число в примере иллюстрирует формат и не задаёт результат модели.

## Ответ insufficient_data

HTTP 200 — это нормальное состояние приложения, не ошибка сервера:

```json
{
  "status": "insufficient_data",
  "calculated_at": "2026-10-20T12:00:00Z",
  "prediction_date": "2026-10-21",
  "time_zone": "UTC",
  "horizon_days": 1,
  "risk_level": null,
  "probability": null,
  "factors": [],
  "recommendations": [],
  "missing_fields": ["caffeine_intake"],
  "message": "Для расчёта заполните сегодняшние значения сна, стресса и кофеина."
}
```

`missing_fields` содержит только отсутствующие поля в порядке сон, стресс, кофеин. При полностью пустом аккаунте будут перечислены все три. Модель в этом состоянии не загружается и не вызывается. После сохранения недостающих полей следующий GET заново проверит состояние; сбрасывать аккаунт не нужно.

## Ошибки

- `401` — нет действительного access-токена; действует существующее обновление сессии.
- `503` — модель не загрузилась или не смогла вернуть корректную вероятность. Ответ: `{"detail":"Прогноз временно недоступен. Повторите запрос позже."}`. Файловые пути и внутренние исключения в ответ не попадают.

Прогноз больше не возвращает `501`. Старое ожидание `501` удалено из Postman. Неисправный файл модели не блокирует запуск авторизации/дневника: загрузка отложена до запроса с достаточными входными данными. После исправления файла следующий запрос может повторить загрузку; при замене уже закешированной модели нужен перезапуск backend.

## Подключение Flutter

1. При загрузке карточки показать индикатор и выполнить GET.
2. При `status=ready` показать `probability * 100`, `prediction_date`, локально отформатированное `calculated_at`.
3. При `status=insufficient_data` убрать прежний процент, показать `message` и предложить заполнить `missing_fields`. `null` нельзя преобразовывать в ноль: настоящий `0.0` допустим только в готовом результате.
4. При `503` или сетевой ошибке показать недоступность и повтор; не выдавать старый процент за новый.
5. После изменения дневника/приступа или смены аккаунта запросить прогноз заново.

Это изменение контракта: существующие имена `probability`, `risk_level`, `factors`, `recommendations` сохранены, но вероятность и строковый процент теперь nullable. Старый код, предполагающий число при каждом HTTP 200, нужно обновить. UI карточки ведётся отдельной задачей.

## История и оценка качества

Сервер исключает будущие даты дневника и приступы, начинающиеся после момента расчёта, в том числе позже в тот же день. Предыдущая логика подсчёта истории по записям дневника сохраняется. Endpoint оценивает текущее состояние БД, не восстанавливает прошлые редакции записей и не предназначен для исторической оценки «как было известно тогда».

Прогнозы не сохраняются автоматически, качество не пересчитывается. Для проверки качества нужна отдельная тестовая выборка/скрипт или журнал прогнозов и будущих исходов. Эту работу выполняет задача ML-разработчицы.

## Ручная проверка

1. Зарегистрировать новый аккаунт. GET должен вернуть `insufficient_data` и `probability=null`.
2. Сохранить через `PUT /diary/{сегодня}` сон, стресс и кофеин (включая `0`). GET должен вернуть `ready`, UTC-время и завтрашнюю локальную дату.
3. Обновить только кофеин до `null`. GET должен перечислить только `caffeine_intake` и убрать вероятность.
4. Проверить другой аккаунт: его готовность и история независимы.

В Postman добавлена папка `Forecast`: она использует локальную дату, вычисленную сервером, и проходит состояния до и после заполнения дневника на тестовом аккаунте коллекции.

Для обновления нужны только новый код и обычные зависимости backend; новая миграция БД не требуется. Существующие наблюдения не меняются.
